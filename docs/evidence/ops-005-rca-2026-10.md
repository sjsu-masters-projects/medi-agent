# OPS-005 / DV-006 root-cause analysis — October 2026

Bounded, read-only analysis of the intermittent "error or endless loading, then success on
retry" reports (clinician Schedule, ADR case and Alerts; patient Visits, Profile, Chat and ADR
follow-up; clinician console Next.js RSC `Failed to fetch`). Source: Cloud Run request logs
for `mediagent-backend` (project `medi-agent-490106`, `us-central1`), window October 9–23 UTC,
queried October 22. Only status, method, latency, revision and route templates were kept; IDs,
query strings and bodies were stripped. No GCP change was made. No browser-side logs from the
original episodes exist, so browser attribution is inferred, not observed.

## Findings

1. **Cold starts were the dominant cause on October 9–11.** CORS preflights (`OPTIONS`) and
   token refreshes took 9.2–44.8 s (median 15.4 s): 55 on Oct 9–11 (15, 23, 17), one more on
   Oct 17. 43 of them were `OPTIONS /api/v1/auth/refresh`, the rest login, feed, documents,
   adherence, clinics, chat history and care-plan routes. A preflight is a tiny request that does
   no database work, so a 10–45 s answer means the request waited for an instance to start. The
   app also started 168 instances for autoscaling between Oct 10 and 20 (Oct 10–19: 9, 24, 16,
   16, 22, 22, 14, 22, 14, 8; Oct 20: 1; none since in the window), each followed by "Application startup
   complete". Client reads have no timeout, so such a page showed endless loading, and the
   one 100–250 ms replay of a failed read could not outlast a 20–40 s start. Revisions up to
   00126 carried an explicit `minScale=0`; the current revisions carry `minScale=1`
   (00189 onward, deployed Oct 22 22:58Z) with CPU boost on and CPU throttling off.
2. **Notification-centre 502s are a second, separate cause.** 70 of 119 backend 5xx (68 are 502, 2 are 500) are
   `GET /api/v1/notification-centre` and `/summary` (plus 44 care-conversations list/recipient
   502s, all on revision 00117 on Oct 10). They return after 6.9–12 s
   (bursts of 2–14 on Oct 10, 12, 13, 16, 17 and 18, the last on Oct 18 06:44Z, revision 00157). That fits the already documented
   notification-pool contention (NOT-001), fixed by a later revision. One straggler: Oct 21 23:13Z
   (revision 00177, 6.9 s). When a Cloud Run 502 has no CORS headers the browser reports a
   transport failure ("Failed to fetch"), not an HTTP error, which matches the console message.
3. **Residual slow/failing reads.** After the notification fix, 5xx are rare: Oct 22 17:00Z
   `POST /cron/chat-turns/dispatch` 502 (11.4 s), Oct 22 ~23:00Z and Oct 23 00:00Z
   `GET /clinicians/me/external-record-reviews` 502 (12.9 s) and 500 (24.2 s), plus two
   write 500s on Oct 13 (care-team join, ADR review; 0.8–1.2 s). The external-record-reviews
   slowness (66 requests of 3 s or more in the window) is unexplained and not on the pages in
   this report; it is out of scope here and should be a follow-up.
4. **Not causes.** There were zero HTTP 499s and zero 408/429s. No 5xx hit schedule
   (`/appointments`), patient profile, or ADR case reads in the window. Most slow successes were
   WebSocket sessions and cron dispatches (expected long-lived requests). The six risk-score
   tracebacks (DV-012) are caught and unrelated.

## Conclusion

Most likely: (a) scale-to-zero cold starts of 18–45 s that hit the preflight/refresh path
(Oct 9–11, concentrated, plus Oct 17), combined with a client with no read timeout and a
replay window too short to survive a start; and (b) notification-endpoint gateway 502s of 7–12 s
that the browser reports as `Failed to fetch`. Both explain "fails, then works on retry" across
every listed page because all of them call `auth/refresh` and a notification poll. The RSC
`Failed to fetch` is consistent with (b)/(a) on the client side, but the Vercel-to-Cloud-Run path
was not logged, so it cannot be proven.

Cannot be proven: that these were the only causes on the reporting days (no per-tab or
browser log exists); the exact cold-start duration after Oct 11 (preflights stopped
exceeding 9 s, probably because traffic was lower and instances stayed warm); and whether
Vercel/Next RSC fetches themselves (server-side) timed out. The 168 autoscaling starts ended
on Oct 20, so min-instances (#221, and a service-level setting before it) appears to prevent
the cold-start class; the live service now shows `minScale=1`.

## Fix

`packages/shared/src/utils/api-transport.ts` (used by both portals' API clients and the
clinician service layer):

* each read attempt now times out after 30 s (`READ_ATTEMPT_TIMEOUT_MS`), so a hung request
  becomes a clear "Could not connect" error with the existing Retry state instead of endless loading;
* a read is replayed once after a timeout, a transport failure, or a 502/503/504 answer
  (400 ms plus jitter), long enough for a started instance to answer;
* writes are never replayed or timed out here, so the unknown-outcome contract is unchanged.

Tests (`apps/*/src/__tests__/api-client.test.ts`, both portals): gateway 502/503/504 replay and
recovery, persistent 502 surfaces after one replay, writes not replayed, hung read times out
and replays, cold-start recovery, and no leaked timers. The old "503 is not replayed" test now
covers HTTP 500, which remains unreplayed.

## Regression guard and what stays open

* Config guard: re-run `gcloud run services describe mediagent-backend` and confirm
  `autoscaling.knative.dev/minScale` is at least 1. A repository-level guard is not possible
  because the service is not deployed from tracked configuration here.
* Watch: `OPTIONS` requests over 5 s and 5xx on notification routes after the deployed
  revision; any recurrence means the cold-start theory is incomplete.
* Open: `external-record-reviews` latency (up to 24 s), a live repeat of the Schedule, ADR,
  Alerts, Visits, Profile and Chat journeys in both portals after the next deploy, and
  clinician RSC `Failed to fetch` that cannot be reproduced from backend logs.
